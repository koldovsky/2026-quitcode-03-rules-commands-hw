# Конвенції коду lead-sync

## Контекст

Воркер ходить у чужі системи по мережі й носить персональні дані лідів. Кожна
конвенція нижче закриває конкретний спосіб зламатися тихо: без таймауту, без
маскування секрету, з «значенням за замовчуванням» замість помилки. Кожну з них
перевіряє `npm run check:rules`.

## Правило

- **Помилки — це значення.** Функція, що може не вдатися, повертає `Result<T>`
  з `core/types.ts`. Не кидай виняток назовні модуля і не лови його мовчки:
  `send()` інтеграції **завжди** повертає `Result<void>`, і на невдачі — `{ ok: false, error }`
  з текстом, за яким видно, що саме сталося.
- **HTTP — лише через `postJson()`** з `app/src/core/http.ts`. Не використовуй прямий
  `fetch` в `integrations/` і `sync/` — у `postJson()` є таймаут, повтори на 5xx/429
  і маскування URL у журналі. Не додавай axios, got, ky чи власну обгортку над `fetch`.
- **Змінні середовища — лише через `readEnv(name)`** з `app/src/core/config.ts`.
  Не читай `process.env` поза `core/config.ts`. Значення секрету не потрапляє ні в
  журнал, ні в текст помилки, ні в код — навіть «тимчасово» і навіть у тест.
- **Зовнішнім даним не довіряй.** Будь-який JSON — відповідь API, тіло вебхука, файл
  стану — розбирай через `parseJson(text, guard)` з guard на очікувану форму
  (`isRecord`, `isString`, `isNumber` з `core/parse.ts`). Не використовуй `JSON.parse`
  напряму. Невалідний JSON або неочікувана форма — це `Result` з `ok: false`, який
  видно в журналі; підставити «значення за замовчуванням» і працювати далі не можна:
  саме так пошкоджений стан робиться непомітним.
- **Журнал — лише через `log`** з `app/src/core/log.ts`. Не використовуй `console.*`
  поза `core/log.ts`: `log` маскує токени, `console.log` друкує їх як є.
- **Без `any`.** Для невідомих даних — `unknown` плюс guard. Не «глуши» тип через
  `as any`, `<any>` чи `@ts-ignore` — якщо тип не сходиться, сходиться не тип, а логіка.
- **Без нових залежностей.** У `app/package.json` нуль runtime-залежностей, і так
  лишається. Не запускай `npm install <пакет>`: потрібна бібліотека — спершу питання
  в PR. У production-файлах імпортуй лише відносні модулі проєкту й вбудовані
  `node:*`. У тестах (`*.test.ts`) додатково дозволений імпорт із `vitest` — це
  devDependency, і `check:rules` тестові файли не сканує.
- **Мінімізація даних.** У сповіщення (Slack, месенджери) йдуть лише ім'я, джерело
  й бюджет. Email і телефон ліда туди не передаються — повні дані лише в системи
  обліку (таблиця, CRM).
- **Імена й імпорти.** Файли — kebab-case; поле `name` інтеграції збігається з іменем
  файлу. Імпорти всередині проєкту — відносні, з розширенням `.js`
  (`import { postJson } from "../core/http.js"`), як у наявних модулях.
- **Тести — Vitest, файл `*.test.ts` поруч із модулем.** Реальної мережі немає:
  `vi.stubGlobal("fetch", ...)`, змінні — `vi.stubEnv`. Перед комітом:
  `cd app && npm test && npm run typecheck && npm run check:rules`.
- **Спадщина.** Код, перенесений з n8n, приводять до конвенцій **окремою задачею і
  без зміни поведінки**: URL, тіло запиту й тексти помилок лишаються тими самими,
  асерти наявних тестів не редагуються. Не «підчищай» його принагідно всередині
  іншої задачі. Виправлення бага — це інша задача, ніж рефакторинг: там зміна
  поведінки і є метою, і вона супроводжується тестом, що падав до фіксу.

## Як перевірити

- `cd app && npm run check:rules` → `TOTAL: 0`. Спадковий код уже приведено до
  конвенцій, тож будь-яке ненульове число в розділі `by rule` — це твоя зміна.
- Рядок у звіті = рядок у правилі: `http-via-core`, `env-via-config`, `json-via-parse`,
  `log-via-logger`, `no-any`, `no-new-deps`.
- `cd app && npm test && npm run typecheck` — зелені.
- Очима в дифі: у тілі сповіщення немає `lead.email` і `lead.phone`;
  `git diff -- app/package.json` не додає секції `dependencies`.
