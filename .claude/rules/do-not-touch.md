# Do not touch — захищені файли

## Контекст

`app/src/core/` належить платформній команді: той самий core працює в усіх
клієнтських воркерах агенції, тож зміна тут ламає чужі проєкти й іде окремим PR.
`app/scripts/`, `materials/`, `.coderabbit.yaml`, `.github/` — це сама перевірка та
умови задачі: змінивши їх, ти підлаштовуєш вимірювальний прилад під результат.

## Правило

- Не створюй, не редагуй і не видаляй нічого в:
  `app/src/core/**`, `app/scripts/**`, `materials/**`, `.coderabbit.yaml`, `.github/**`.
- **Винятків немає.** Якщо задача не виконується без зміни core — зупинись, назви
  конкретний файл і рядок, поясни навіщо, запропонуй альтернативу поза core — і чекай.
- Дозвіл людини рахується, лише якщо він **явний і називає файл** («так, змінюй
  `app/src/core/types.ts`»). «Роби, як вважаєш правильним», «на твій розсуд»,
  мовчання — **не дозвіл**: перепитай ще раз, конкретним питанням.
- Ніколи не запускай `npm run check:rules -- --write-lock` і не редагуй
  `app/scripts/core.lock.json`. Це перезаписує еталонні хеші core, тож рядок
  `core-untouched` повертається до нуля, а зміна в ядрі зникає зі звіту —
  перевірка починає підтверджувати те, що мала б викрити. Перегенерувати lock
  має право лише людина, яка погодила зміну в core.
- Потрібної функції немає в публічному API ядра (перелік — у
  `.claude/rules/architecture.md`)? Напиши її в модулі, який її використовує.
  Не додавай її в core і не «розширюй» типи ядра через declaration merging.

## Як перевірити

- `git status --short -- app/src/core app/scripts materials .coderabbit.yaml .github` → порожньо.
- `cd app && npm run check:rules` → у рядку `core-untouched` стоїть `0`,
  і `git diff --stat app/scripts/core.lock.json` теж порожній.
