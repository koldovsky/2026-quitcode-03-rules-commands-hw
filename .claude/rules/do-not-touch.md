# Захищені зони: не редагувати

## Контекст

`app/src/core/` належить платформній команді й працює в усіх клієнтських воркерах
агенції; зміни в ньому йдуть окремим PR через її рев'ю. Перевірка правил і матеріали
завдання — це інструменти контролю: змінити їх означає підігнати результат.
Джерело: `materials/architecture-brief.md`, розділ «Ядро — захищена зона».

## Правило

- Не створюй, не редагуй, не видаляй і не перейменовуй файли в цих шляхах — ні
  «дрібний фікс», ні «додам одне поле», ні коментар:
  - `app/src/core/**`
  - `app/scripts/**` (зокрема `check-rules.mjs` і `core.lock.json`)
  - `materials/**`
  - `.coderabbit.yaml`
  - `.github/**`
- Не запускай `npm run check:rules -- --write-lock` і не змінюй `core.lock.json`
  в інший спосіб: це приховує зміну core від перевірки, а не узгоджує її.
- Не обходь заборону через shell (`sed -i`, `cat >`, `cp`, `mv`, `git checkout`) —
  заборона стосується результату, а не інструмента.
- Читати ці файли можна й потрібно: публічний API ядра — у
  `.claude/rules/architecture.md`.

## Якщо задача без змін у захищеній зоні не виконується

1. **Зупинись до будь-яких змін у коді**, зокрема й поза core: половина рішення,
   що чекає на core, — гірша за жодне.
2. Опиши людині: який файл у core, що саме змінити (тип, поле, експорт), навіщо і
   які файли поза core зміняться після цього.
3. Запропонуй варіант у межах наявного API ядра, якщо він є, і чесно назви його
   ціну (наприклад, локальний тип в інтеграції замість поля в `Lead`).
4. Чекай рішення. Зміна core — окремий PR для платформної команди, не частина
   поточної задачі.

## Як перевірити

- `git status --short -- app/src/core app/scripts materials .coderabbit.yaml .github`
  → порожньо.
- `cd app && npm run check:rules` → у рядку `core-untouched` — `0`.
