# refactor

**Ціль:** $ARGUMENTS
(Якщо в рядку вище немає конкретного файлу — ціль вказана в повідомленні
одразу після назви команди. Немає й там — спитай і зупинись.)

## Кроки

1. Перед зміною: `cd app && npm run check:rules` — запиши кількість порушень
   для цільового файлу (розділ "by file") і `npm test` — запиши, скільки
   тестів зелені.
2. Приведи файл до `.claude/rules/conventions.md` і `.claude/rules/architecture.md`
   (посилайся на них, не копіюй сюди): `Result<T>` замість винятків, `postJson`
   замість `fetch`, `readEnv` замість `process.env`, `parseJson(text, guard)`
   замість `JSON.parse`, `log` замість `console.*`, без `any`, без нових
   залежностей.
3. Не змінюй зовнішню поведінку: URL, тіло запитів, тексти помилок мають
   лишитись такими самими, як фіксують наявні тести.
4. Після зміни: ті самі команди — `npm run check:rules` (кількість для файлу
   зменшилась/дорівнює 0) і `npm test` (усі тести й далі зелені, без
   редагування асертів).

## Acceptance criteria

- [ ] `check:rules` для цільового файлу: після ≤ до (в ідеалі 0); якщо
      частину порушень не можна усунути без зміни `core/` — записано, чому.
- [ ] `npm test` зелений і до, і після; жодного асерту в тестах не змінено.
- [ ] Змінено лише вказаний файл (і, за потреби, лише сам його тест-файл — без
      зміни асертів); жодного іншого модуля в `integrations/`, `sync/`,
      `core/`.
- [ ] Поведінка (URL, тіло запиту, текст помилки) ідентична до і після.

## Stop

Якщо усунути порушення неможливо, не чіпаючи інших файлів чи `app/src/core/**` —
зупинись, поверни файл як був, і опиши, що саме заважає й що потрібно
змінити. Не редагуй асерти в тестах, щоб "підігнати" їх під нову поведінку.
