## Тригер

Заповнення диска нічним backup-джобом (`00:02:37`, 97% → 100%, звільнено о `00:13:48`) — зовнішня, разова подія, не пов'язана з кодом воркера.

## Причина

`app/src/sync/run.ts:36` — `saveState` викликається **рівно один раз, після того як цикл `for (const lead of pending) { for (const integration...) }` (рядки 24–30) повністю відпрацює для всього пакету**. Немає інкрементального збереження прогресу на рівні ліда чи чанку. Тож будь-яке аварійне завершення прогону до рядка 36 — крах, `SIGKILL` від планувальника — відкидає прогрес усього пакету, і `lastSyncedAt` не рухається, хоча частину лідів уже реально доставлено.

## Прив'язка до доказу

Найконкретніший рядок: `2026-09-10T00:20:00.384Z INFO slack-notify: lead ld_0001 delivered` — це **той самий** `ld_0001`, що вже пішов о `00:15:00.377`. Моя гіпотеза це пояснює: прогін `00:15:00` не дійшов до `saveState` (killed о `00:19:30`), тож `lastSyncedAt` лишився старим, і `ld_0001` знову потрапив у `pending` на наступному прогоні.

Конкуруюча гіпотеза: «причина — рейт-лімітинг Slack (`HTTP 429`)». Вона пояснює `WARN`/`ERROR` навколо `00:18:12–00:18:13`, але **не пояснює** саме рядок `00:20:00.384 … ld_0001 delivered`: рейт-ліміт Slack — це тимчасове обмеження на секунди, воно не змушує систему через 5 хвилин знову розсилати вже успішно доставлений `ld_0001` з початку пакету. Без механізму «стан не зберігся» цей рядок не має пояснення.

Гіпотеза неповна без другого механізму — вона пояснює, чому інцидент *не припиняється*, але не чому одиничний прогін *почав* перевищувати 4м30с. Другий механізм: `core/http.ts`'s `postJson` retry/backoff (2 повтори, `backoffMs * attempt`) плюс послідовна (не паралельна, не чанкована) обробка `leads × integrations` у `run.ts` — при накопиченому за ~13 хв пакеті (сотні лідів) і рейт-лімітах Slack сумарний час прогону перевищує жорсткий ліміт планувальника 4м30с, після чого `SIGKILL` відбувається саме в середині циклу.

## Тест на фальсифікацію

- **«Тригер повторився, причину виправлено — інцидент станеться?»** Ні. Якщо диск знову заповниться, кілька прогонів впадуть з `ENOSPC` (як о 00:05 і 00:10) — це неприємно, але тимчасово. Якщо `run.ts` зберігає прогрес інкрементально, після звільнення диска накопичений пакет розійдеться без вічного дублювання: кожен успішно надісланий лід зафіксується, навіть якщо якийсь прогін не встигне за 4м30с.
- **«Причину не чіпали, тригер прибрано — інцидент припиниться сам?»** Ні — і це видно прямо в лозі: тригер зник о `00:13:48`, а паттерн «розсилка → SIGKILL → та сама розсилка» триває щонайменше до `09:14:30`. Отже кандидат «диск» — це саме тригер, а не причина; причину слід шукати в коді (крок 3), що й було зроблено.

## Підсилювачі

- `core/http.ts` — retry/backoff на `429` додає затримку кожному запиту в уже величезному пакеті, зближуючи час прогону з лімітом 4м30с.
- `run.ts:24-30` — послідовна обробка `for lead → for integration` без чанкування/паралелізму: час прогону росте лінійно з розміром `pending`, без верхньої межі.
- Планувальник (поза репо, `worker.ts`/деплой) — жорсткий `SIGKILL` за 4м30с без graceful-shutdown чи сигналу зберегти стан перед вбивством.
- Зростання `pending` компаундиться: нові ліди й далі надходять кожні 5 хв, поки `lastSyncedAt` не зрушується → кожен наступний пакет лише більший за попередній, і йому ще важче вкластися в 4м30с.

## Тест-відтворення (лише показую, у файл не пишу)

`app/src/sync/run.test.ts`, поруч із наявними тестами:

```ts
it("падіння всередині пакета не повинне призводити до повторної розсилки вже надісланих лідів", async () => {
  const sent: string[] = [];
  const statePath = join(dir, "sync-state.json");
  const flaky: Integration = {
    name: "flaky",
    requiredEnv: [],
    send: async (lead) => {
      sent.push(lead.id);
      if (lead.id === "ld_0003") throw new Error("worker killed mid-run");
      return { ok: true, value: undefined };
    },
  };

  await expect(runSync(leads, [flaky], statePath)).rejects.toThrow();
  sent.length = 0;

  await runSync(leads, [flaky], statePath).catch(() => {});

  expect(sent).not.toContain("ld_0001"); // вже доставлений у першому прогоні — не повинен піти вдруге
});
```

На поточному коді `sent` міститиме `ld_0001` вдруге (`toContain` спрацює, `not.toContain` — впаде), бо `lastSyncedAt` не зрушився після аварійного завершення. Емуляція `SIGKILL` через `throw` у `send` — найближчий доступний у юніт-тесті проксі: справжній `SIGKILL` не відтворити в процесі, але наслідок («цикл не дійшов до `saveState`») ідентичний.

## План фіксу

1. **`app/src/sync/run.ts`** — зберігати `lastSyncedAt` інкрементально: після кожного успішно обробленого ліда (обидві інтеграції відпрацювали) викликати `saveState` з `createdAt` цього ліда, а не один раз після всього циклу (зараз рядок 36). Чому: обмежує «зону ризику» одним лідом замість усього пакету — аварійне завершення втратить прогрес щонайбільше по одному ліду, а не по сотнях.
2. **`app/src/sync/run.ts`** — рішення для випадку, коли одна з інтеграцій для ліда провалилась (`result.ok === false`): чи рухати checkpoint далі, чи ні. Треба явно визначити семантику (найризикованіший пункт, див. нижче), інакше зміна з п.1 тихо змінить поведінку, яку зараз фіксують тести на `failed`.
3. **`app/src/sync/run.ts`** (опційно, друга частина фіксу) — бюджет часу на прогін: відстежувати `Date.now()` від старту і, наближаючись до лімітів планувальника, зупинити обробку та вийти з уже збереженим станом, залишивши решту `pending` на наступний прогін. Це не потребує нових API з `core/` — лише `Date.now()`, який уже доступний без імпортів.
4. Обидва пункти лишаються в `sync/`, не торкаються `core/**` — відповідає `architecture.md` (`sync/` не імпортує нічого нового з core, публічний API ядра не розширюється).

**Найризикованіший пункт — №2**: зміна моменту, коли `lastSyncedAt` рухається вперед за часткового провалу однієї з інтеграцій. Якщо просувати checkpoint навіть при `failed`, провалений лід ніколи не retry-иться повторно (мовчазна втрата) — а конвенції явно забороняють мовчазні дефолти для пошкоджених/неповних даних. Якщо не просувати — лід із хронічно неробочою інтеграцією (напр. невірний webhook) назавжди блокуватиме checkpoint і відновить стару поведінку «весь хвіст переробляється». Це рішення варто узгодити з тобою окремо, а не вирішувати мовчки в реалізації.
