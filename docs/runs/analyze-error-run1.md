## 2. Тригер

Тригер — зовнішня, разова подія: нічний бекап-джоб заповнив диск `/srv/lead-sync/data` до 97–100% (00:02:37–00:05:00), через що `writeFileSync` у `saveState` двічі впав з `ENOSPC` (00:05, 00:10). Об 00:13:48 диск сам звільнився (архів видалено), і тригер зник назавжди — жодного повторного `ENOSPC` у лозі більше немає.

## 3. Причина

`app/src/sync/run.ts:36` (у парі з єдиним викликом `saveState` в кінці функції, рядок 18 лише дублює цей запис на старті) — механізм: `runSync` оновлює `lastSyncedAt` на диску **рівно один раз, після того як усі pending-ліди пройшли через усі інтеграції**. Якщо прогін не доходить до рядка 36 (крах, або зовнішній `SIGKILL` планувальника на 4х30с), прогрес усередині цього прогону ніде не зберігається — наступний тик читає той самий старий `lastSyncedAt` і надсилає **весь той самий пакет лідів заново**. Оскільки після відновлення диска (00:15) назбирався великий backlog, його послідовна обробка (`for lead of pending { for integration ... await send() }`, без паралелізму) сама почала впиратись у ліміт 4х30с — і кожен наступний прогін гарантовано вбивається `SIGKILL`, ніколи не доходячи до `saveState` в кінці. Це перетворило разовий збій диска на нескінченний цикл дублювання.

## 4. Тест на фальсифікацію

**«Тригер повторився, причину виправлено — інцидент станеться?»**
Ні. Якщо `saveState` викликати інкрементно (після кожного успішно обробленого ліда), то новий `ENOSPC` знову спричинить кілька невдалих прогонів під час заповнення диска — але вже надіслані ліди на той момент вже будуть зафіксовані в стані. Після зникнення тригера наступний прогін надішле лише реальний залишок, без розсилки вже доставлених лідів. Отже кандидат — справжня причина: без неї повторний тригер дає лише коротку паузу, а не 9-годинний дубль-шторм.

**«Причину не чіпали, тригер прибрано — інцидент припиниться сам?»**
Ні, і лог це підтверджує напряму: тригер зник о 00:13:48, а дублювання й `SIGKILL` тривали щонайменше до 09:14:30 (востаннє зафіксовано в лозі) без жодної ознаки завершення. Раз симптоми пережили зникнення тригера на ~9 годин, кандидат-«причина» справді причина, а не ще один тригер, — крок 3 підтверджено, повертатись назад не потрібно.

## 5. Підсилювачі

- **Послідовна обробка без конкурентності** (`run.ts:24-30`, вкладені `for` з `await` по черзі) — час прогону росте лінійно з розміром backlog'у, який після першого зникнення стану вже ніколи не зменшується сам; це і штовхнуло прогін за межу 4х30с.
- **Retry/backoff на 429 у `postJson`** (`core/http.ts`, чіпати не можна) — коли Slack почав рейт-лімітити через масову розсилку, кожен лід отримав додаткові 300–600мс затримки на повтори, що ще сильніше подовжило прогін саме в момент, коли він і так уже був на межі таймаута.
- **Відсутність ідемпотентності в інтеграціях** (`slack-notify.ts`, `sheets-append.ts`) — жодна з них не перевіряє, чи лід уже надсилався, тож кожен повторний прогін сліпо дублює повідомлення й рядки в таблиці.
- **Жорсткий `SIGKILL` планувальника без graceful shutdown** (поза цим репозиторієм, `worker.ts`) — перериває процес миттєво, не даючи шансу зберегти хоч частковий прогрес.

## 6. Тест, що відтворює проблему

Файл (гіпотетично) `app/src/sync/run.test.ts`, новий кейс поруч з наявними двома — у файл не пишу.

```ts
it("переривання прогону перед фінальним saveState призводить до повторної відправки вже надісланих лідів", async () => {
  const statePath = join(dir, "sync-state.json");
  const sent: string[] = [];

  const crashingIntegration: Integration = {
    name: "crashing",
    requiredEnv: [],
    send: async (lead) => {
      sent.push(lead.id);
      if (lead.id === "ld_0003") throw new Error("simulated SIGKILL mid-run");
      return { ok: true, value: undefined };
    },
  };

  // перший тик: обробив ld_0001, ld_0002, впав на ld_0003 — так і не дійшов до run.ts:36
  await expect(runSync(leads, [crashingIntegration], statePath)).rejects.toThrow();

  // ФАЛЬШИВЕ твердження на поточному коді: стан не просунувся,
  // хоча ld_0001 і ld_0002 вже пішли в Slack/Sheets
  expect(JSON.parse(readFileSync(statePath, "utf8"))).toEqual({
    lastSyncedAt: "1970-01-01T00:00:00.000Z",
  });

  // наступний тик планувальника (той самий leads-масив, як у продакшені)
  await runSync(leads, [crashingIntegration], statePath).catch(() => {});

  // ld_0001 і ld_0002 надіслані ДВІЧІ — це і є дублікати з інциденту
  expect(sent).toEqual([
    "ld_0001", "ld_0002", "ld_0003",
    "ld_0001", "ld_0002", "ld_0003",
  ]);
});
```

На поточному `run.ts` перше твердження (`lastSyncedAt` не змінився) — істинне, а останнє (`ld_0001`/`ld_0002` двічі в `sent`) — це і є дубль, який бачить клієнт.

## 7. План фіксу

1. **`app/src/sync/run.ts:20-38`** — зберігати `lastSyncedAt` одразу після кожного успішно обробленого ліда (усіма інтеграціями для цього ліда), а не одним `saveState` наприкінці. Чому: тоді переривання (крах або `SIGKILL`) втрачає прогрес щонайбільше по одному ліду, а не по всьому пакету — наступний тик не передублює вже надіслане. Не виходить за публічний API ядра — `saveState`/`loadState` з `core`-подібного модуля `sync/state.ts` вже є, міняється лише місце виклику.
2. **`app/src/sync/run.ts:18`** — прибрати початковий «холостий» виклик `saveState(statePath, state)` (просто переписує файл тим самим вмістом на кожному тику). Чому: це другий з двох `ENOSPC`-крашів у лозі (00:05 і 00:10) і зайвий запис на диск на кожному з 288 прогонів на добу без жодної користі — `loadState` вже сама повертає `INITIAL_STATE`, коли файлу немає, писати його одразу не обов'язково.
3. **`app/src/sync/state.ts:20-22`** (`saveState`) — писати атомарно: спершу у тимчасовий файл, потім `renameSync` на цільовий шлях. Чому: зараз `writeFileSync` пише напряму; обрив запису (диск скінчився/`SIGKILL`) може лишити пошкоджений JSON, а `loadState` (`state.ts:13-17`) тихо ковтає помилку парсингу й відкочується до 1970 року — тобто один невдалий запис спричинить повторну розсилку **взагалі всієї історії лідів**, що гірше за поточний інцидент. `renameSync` у межах однієї файлової системи атомарний, тож обірваний запис ніколи не підмінить валідний файл.
4. **Поза цим репозиторієм** (`worker.ts`, деплой-репо) — повідомити власника: ліміт 4х30с і `SIGKILL` без graceful shutdown лишаються. П.1–3 зупиняють дублювання, але не сам факт, що дуже великий backlog може не встигнути за один тик; варто розглянути пом'якшення на боці планувальника (більший ліміт або обробка частинами), але це не зміна в цьому репозиторії.

Пункти 1–3 узгоджені з `.claude/rules/architecture.md` (жодного нового імпорту з `core/`, зміни лише в `sync/`) і `conventions.md` (без нових залежностей, без `any`, `Result<T>` де це вже застосовується).

## Найризикованіший пункт

Пункт **1** (перенесення `saveState` всередину циклу обробки лідів) — найризикованіший: він змінює контрольний потік `runSync` і зачіпає поведінку, зафіксовану тестами (`run.test.ts`) — зокрема те, що `lastSyncedAt` після повного успішного прогону має дорівнювати найновішій даті серед *усіх* pending-лідів незалежно від `failed`. Легко ненавмисно змінити семантику для лідів, у яких відмовили всі інтеграції (зараз вони все одно «проковтуються» назавжди), або зламати підрахунок `pending/delivered/failed` у звіті.
